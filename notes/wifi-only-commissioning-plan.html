Wi-Fi-Only Commissioning via USD

Feasibility assessment and phased implementation plan for supporting Matter 1.4.2's Wi-Fi Unsynchronized Service Discovery (USD) commissioning flow — onboarding a device with no Bluetooth LE radio at all.

Prepared 2026-08-21 chip submodule pin efefc94f esp-matter target IDF v6.0.2
Verdict

Feasible, and less far off than it looks — but not a small PR. The two hardest prerequisites are already satisfied upstream: ESP-IDF's Wi-Fi radio driver already speaks NAN-USD, and connectedhomeip's core protocol engine and onboarding-payload plumbing for WiFiPAF already exist. What's actually missing is a full ESP32 platform binding in connectedhomeip (nobody has written it yet — only Linux has one) plus the esp-matter wiring on top of it. That's a real feature, best scoped as multiple phases and ideally contributed upstream rather than kept in Espressif's fork alone.

What Matter 1.4.2 changed

Today, esp-matter devices commission over one of two transports: kBLE (a BLE GATT rendezvous, then handoff to Wi-Fi) or kOnNetwork (the device is already on the IP network and gets discovered over mDNS — used for re-commissioning or same-network flows). Neither works for a device that has never joined Wi-Fi yet and has no BLE radio.

Matter 1.4.2 closes that gap using Wi-Fi's Unsynchronized Service Discovery (USD) — a lightweight publish/subscribe mechanism from the Wi-Fi Aware (NAN) family that lets two nearby devices find and exchange short messages over 802.11 without joining a network first. Connectedhomeip calls its implementation WiFiPAF (Wi-Fi Proximity Access Framework); the onboarding payload already carries a dedicated bit for it.

Per-chip NAN radio support ESP-IDF / hardware confirmed broad ESP-IDF's own supported-targets table for usd_publisher/usd_subscriber lists ESP32, C2, C3, C5, C6, C61, S2 and S3 — no build-system target gating beyond the CONFIG_ESP_WIFI_NAN_USD_ENABLE Kconfig flag. NAN discovery runs over standard 802.11 action frames, not a Wi-Fi-6-specific mechanism, so this isn't limited to the newest radios.
Follow-up frame payload vs. PAFTP MTU ESP-IDF ↔ connectedhomeip compatible PAFTP's fragment size is CHIP_PAF_DEFAULT_MTU = 350 bytes (WiFiPAFConfig.h:150), chosen against the Wi-Fi Aware spec's own "Supported Maximum Service Specific Info Length" (comment at WiFiPAFTP.cpp:70-72). ESP-IDF's wifi_nan_followup_params_t.ssi is a variable-length pointer, capped at ESP_WIFI_MAX_FUP_SSI_LEN = 2048 bytes — comfortably above 350. Publish/subscribe SSI caps at ESP_WIFI_MAX_SVC_SSI_LEN = 512, also above it.
USD as a first-class discovery mode (vs. synced-NAN-only) ESP-IDF confirmed wifi_nan_publish_cfg_t / wifi_nan_subscribe_cfg_t carry a dedicated usd_discovery_flag bit and an embedded wifi_nan_usd_config_t. The shipped usd_publisher_example_main.c (v6.0.2) sets usd_discovery_flag = 1, calls esp_wifi_nan_publish_service(), and sends real payloads through esp_wifi_nan_send_message() — a working, non-stub code path, not NAN-cluster-sync bolted on.
Commissioner-side support out of scope (controller/mobile) unverified chip-tool has some Linux-side pairing support; mainstream mobile commissioners (Apple Home, Google Home, Alexa) readiness is unconfirmed — tracked informally in home-assistant discussion #1060.

Phased plan

00
Scope · ~1–2 days

Verify & align

Three of four open questions are now resolved; one remains.

  • Check out connectedhomeip/connectedhomeip at the pinned SHA and confirm whether the upstream wifipaf core is already present. — done: confirmed present (src/wifipaf/, kWiFiPAF), ESP32 binding confirmed absent.
  • Confirm the ESP-IDF NAN API isn't synced-cluster-only and that follow-up frames can actually carry PAFTP's fragment size. — done: usd_discovery_flag + wifi_nan_usd_config_t make USD a first-class mode, and the 2048-byte follow-up SSI cap comfortably covers PAFTP's 350-byte MTU. Full numbers in the row above.
  • Confirm which target chips actually expose NAN/USD. — done: ESP-IDF's own supported-targets table for the USD examples covers ESP32, C2, C3, C5, C6, C61, S2 and S3, gated only by a Kconfig flag, not per-chip build restrictions.
  • Still open — and now in progress: on-air timing/reliability. A header-level API check isn't a substitute for measuring a real multi-fragment follow-up exchange against PASE's retransmit/timeout budget. A standalone spike (burst of CHIP_PAF_DEFAULT_MTU-sized fragments over the stock usd_publisher/usd_subscriber examples, run on two ESP32-C6 boards) is the concrete next action before writing the platform binding.
  • Open a tracking discussion upstream in project-chip/connectedhomeip — an ESP32 WiFiPAF platform binding is exactly the kind of thing worth landing there instead of only in Espressif's fork, so it doesn't rot on every future sync.
01
connectedhomeip · largest chunk

ESP32 platform binding for WiFiPAF

Mirror the Linux binding's shape, but drive ESP-IDF's NAN-USD C API instead of wpa_supplicant.

  • New src/platform/ESP32/ConnectivityManagerImpl_WiFiPaf*.{h,cpp}, implementing the same delegate interface as ConnectivityManagerImpl_WiFiPafInterface.
  • Map WiFiPAF publish/subscribe/follow-up onto wifi_nan_publish_cfg_t, wifi_nan_subscribe_cfg_t, wifi_nan_followup_params_t, and the wifi_event_nan_svc_match_t / wifi_event_nan_receive_t event callbacks.
  • Wire it into WiFiPAFLayerDelegate so the existing protocol-agnostic engine (fragmentation, session lifecycle) is reused as-is.
02
esp-matter

Kconfig & commissioning wiring

  • New Kconfig toggle (e.g. CONFIG_ENABLE_WIFIPAF_COMMISSIONING) analogous to the existing CONFIG_USE_BLE_ONLY_FOR_COMMISSIONING pattern in esp_matter_core.cpp.
  • Set kWiFiPAF in the rendezvous/discovery-capabilities bitmask when generating the onboarding payload (mirrors how esp_matter_controller_commissioning_window_opener.cpp:95 sets kOnNetwork today).
  • Make the BLE stack fully excludable at build time when WiFiPAF is the chosen transport, not merely shut down post-commissioning.
  • Update mfg_tool QR/manual-code generation to reflect the new capability bit.
03
Examples & docs

Reference implementation

  • A BLE-less commissioning path in an existing example (the light example, gated by the new Kconfig) rather than a brand-new example app.
  • Developer docs page walking through pairing with a NAN-USD-capable commissioner — realistically chip-tool on Linux first, since mobile-commissioner readiness is unconfirmed.
04
Validation

Test matrix

  • End-to-end pairing against chip-tool over a NAN-capable adapter, on ESP32-C6 first.
  • Regression pass confirming kBLE and kOnNetwork flows are untouched.
  • Certification implications flagged separately — a new commissioning transport likely needs test-plan coverage beyond code review.

Risks & open questions

  • Hardware scope. NAN/USD needs specific radio timing support; don't commit to "every ESP32 variant" until the per-chip matrix is confirmed. C6/C5/C61 are the safe first bet.
  • Ecosystem readiness. Device-side support is necessary but not sufficient — the feature only helps end users once mainstream commissioner apps add WiFiPAF support. That's tracked loosely elsewhere (e.g. Home Assistant's own discussion) and is outside esp-matter's control.
  • Upstream vs. fork. The ESP32 platform binding belongs in project-chip/connectedhomeip, not only in Espressif's fork — otherwise every fork sync risks re-losing it.
  • Certification. A new rendezvous transport typically needs Matter test-plan (TE) coverage, which is a separate process from the code itself.

Recommended next step

Post the findings above as a comment on issue #1825 — mainly to surface that the ESP-IDF radio layer and the connectedhomeip core protocol are already there, so the real ask is scoped down to "write the ESP32 platform binding + esp-matter wiring," and to ask maintainers whether Espressif already has this in progress internally before anyone starts Phase 1 blind.
